# Email Basics

Read this page before you write mail markup: it explains how to research client support, how MJML nests content, and why base styles must be inline.

## Research Before You Code

Email development is different from web development. Email clients do not share a rendering engine. The most constrained major client, Outlook on Windows (2007–2019), uses **Microsoft Word** to render HTML and supports only a small part of modern CSS. Its global market share is small, but it is the main client in enterprise and B2B environments. Markup that works in a browser often breaks in email clients.

Before you implement a visual technique, **verify its support across email clients**. This includes techniques that seem basic, such as rounded corners, background images, custom fonts, or flexbox layouts. Many common CSS properties have partial or no support.

### The Research Habit

When you implement a visual feature:

1. Check [Can I email](https://www.caniemail.com/) for the CSS properties and selectors involved.
2. If Outlook does not support a property, search for a VML workaround or provide a graceful fallback. Square corners are acceptable unless the design requires rounded ones; then add VML (see [No CSS `border-radius` in Outlook](?path=/docs/docs-email-client-pitfalls--docs#no-css-border-radius-in-outlook)).
3. Test in Storybook with the MJML Warnings panel open.
4. When you are not sure, look in the Litmus blog or the Campaign Monitor guide for known patterns.

This also applies to properties that seem simple: `border-radius`, `background-image`, `flexbox`, `gap`, and custom fonts all have partial or no support in major email clients.

For which selectors reach which clients, see [Selectors That Reach Every Client](?path=/docs/docs-email-client-pitfalls--docs#selectors-that-reach-every-client).

## The MJML Layout Model

MJML enforces a strict **section → column → content** nesting hierarchy:

- **`MjmlSection`** — a full-width horizontal row
- **`MjmlColumn`** — divides a section into vertical columns
- **Content components** (`MjmlText`, `MjmlImage`, `MjmlButton`, etc.) — placed inside a column

Content components outside this hierarchy cause MJML validation warnings and broken layouts. The MJML Warnings panel in Storybook shows these warnings during development.

```tsx
<MjmlSection indent>
    <MjmlColumn>
        <MjmlText variant="heading">Section title</MjmlText>
        <MjmlText variant="body" bottomSpacing>
            Body paragraph with spacing below.
        </MjmlText>
        <MjmlImage src="https://example.com/image.jpg" alt="Example" />
    </MjmlColumn>
</MjmlSection>
```

### Multi-Column Layouts

MJML has no `gap` property: padding on the inner edges of adjacent columns makes the gap (see [How Column Gaps Work](?path=/docs/docs-layout-patterns--docs#how-column-gaps-work)). Set `disableResponsiveBehavior` on **every** section with more than one column, and write the mobile stacking with `registerStyles` (see [Column Widths Must Be Inline](?path=/docs/docs-layout-patterns--docs#column-widths-must-be-inline)).

```tsx
const columnGap = 20;
const halfGap = columnGap / 2;

<MjmlSection indent disableResponsiveBehavior className="twoColumnsSection">
    <MjmlColumn className="twoColumnsSection__leftColumn" paddingRight={halfGap}>
        <MjmlText>Left column</MjmlText>
    </MjmlColumn>
    <MjmlColumn className="twoColumnsSection__rightColumn" paddingLeft={halfGap}>
        <MjmlText>Right column</MjmlText>
    </MjmlColumn>
</MjmlSection>;
```

For complete patterns — two columns, three or more, fixed+fluid — with responsive styles, CSS targeting rules, the stacking strategies, and the `direction="rtl"` technique for controlling mobile stack order, see [Layout Patterns](?path=/docs/docs-layout-patterns--docs).

### Ending Tags

Some MJML components are [**ending tags**](https://documentation.mjml.io/#ending-tags) — they accept raw HTML as children but **cannot** contain other MJML components. The most common: `MjmlText`, `MjmlButton`, `MjmlTable`, `MjmlRaw`.

Inside an ending tag, the **entire subtree is HTML**. Use HTML elements (`<span>`, `<a>`, `<table>`, `<td>`), not MJML components. The library provides `HtmlText` and `HtmlInlineLink` for themed text and links inside ending tags.

For raw HTML layouts outside text, use `MjmlRaw` (or `MjmlTable`). These are escape hatches for cases that MJML components cannot handle. Use them only as a last resort.

## The Styling Model

Email clients that lack CSS support are almost all desktop clients (Outlook 2007–2019, older Lotus Notes). Apple Mail, the Gmail app with a Google account, and Outlook mobile support `<style>` blocks and media queries. Gmail's mobile webmail and the Gmail apps with a non-Google account drop media queries. So email styling follows a **desktop-first** approach:

1. **Base/default styles are inline** — applied through MJML component props or explicit `style` attributes on HTML elements. Desktop clients like Outlook ignore `<style>` blocks entirely, so the base rendering must look correct with inline styles alone.

2. **Responsive overrides are progressive enhancement** — registered via `registerStyles` with media queries targeting mobile viewports. Most clients that support media queries also support modern CSS, so properties like `flex` are safe inside media queries. `calc()` is an exception: Yahoo Mail and Outlook.com drop it (see [No CSS `calc()`](?path=/docs/docs-email-client-pitfalls--docs#no-css-calc)).

3. **`!important` is required** in media query overrides — because inline styles take precedence over `<style>` block rules, responsive overrides need `!important` to win.

Never rely on `<style>` blocks for base/desktop layout. Set all default styles inline via MJML component props. MJML breaks this rule for column widths, see [Multi-Column Layouts](#multi-column-layouts).

Reading a `<style>` block is not the same as applying everything in it. Gmail reads the block and then drops each rule whose selector it does not take — see [Selectors That Reach Every Client](?path=/docs/docs-email-client-pitfalls--docs#selectors-that-reach-every-client).

For the `registerStyles` API, the `css` helper, and custom components, see [Styling and Customization](?path=/docs/docs-styling-and-customization--docs).
